# CLAUDE.md

Guidance for working in this repo. Project background and scope live in [README.md](README.md).

## Project

GridLoad: an Android app that shows whether now is a good time to run household appliances, based on dynamic electricity prices.

## Stack

- Native Android: Kotlin + Jetpack Compose, single Activity. One main screen, plus Settings, the setup guide and the history. Distributed via F-Droid and Obtainium (GitHub Releases).
- No Flutter / React Native / KMP. No proprietary dependencies (Firebase, Play Services, analytics, ads). Permissions: `INTERNET`, and for the whatwatt `ACCESS_LOCAL_NETWORK` and `VIBRATE` (the in-app peak alarm) (user, 2026-10-02; see [Peak load with whatwatt](#peak-load-with-whatwatt)).
- A small `core` package with no Android dependencies holds the regions, the API client, the JSON model, the classification, the price cache, the whatwatt client, the recorder (its script as a resource, the day files, the checks), the quarter-hour logic and the appliances (the model, measuring, variants, OK/WAIT). Unit-test it directly.
- Detailed build plan and progress: [.claude/skills/build-gridload-android/SKILL.md](.claude/skills/build-gridload-android/SKILL.md). Where it and this file disagree, this file wins.

There is no default region: the first start ends with a region choice, and nothing is fetched before it. Installs from v0.2, which never saved a region, fall back to CKW. Switching region drops the cached slots, resets the cooldown and fetches.
- Refresh policy (because of the rate limit): one response covers today and, once published, tomorrow. So on resume and every minute while visible, recompute the colour from the cached slots, and fetch only when no slot covers now, when it's after the region's `tomorrowFrom` and the cache doesn't reach tomorrow yet (`wantsFetch`), or when the user pulls down to refresh (no button since 2026-10-03). That's about two fetches a day. Fetches the user didn't ask for always wait the full 5-minute cooldown. Never fetch more often than a cooldown: 5 minutes after any attempt that may have reached the server (successful or not; one that failed for lack of a connection, i.e. no DNS, refused or no route, doesn't count, `reachedServer`), or 30 seconds when nothing is shown, so refreshing repeatedly can't hit the rate limit (`Cooldown.kt`). A blocked refresh shows a short notice instead, and while it would be blocked the ↻ in the "Updated" line is dimmed (`cooldownEnd`). The last response is saved in `files/prices.json` (`PriceCache`: the API's JSON plus the region id and fetch time) and used on the next start if it's the region's and still covers now, so the colour shows at once, offline too; the last attempt is saved as `last_fetch_attempt`, so the cooldown survives a restart. The polling loops run in `lifecycleScope` with `repeatOnLifecycle(STARTED)` in `MainActivity.onCreate`. A failed fetch shows a short message by kind (busy, error code, no connection, unreadable), not the exception's text.
- Saved in SharedPreferences (`settings`): `region`, `first_start_done`, `last_fetch_attempt`, `whatwatt_enabled`, `whatwatt_address`, `power_unit` (`"kW"` or `"W"`), `peak_enabled`, `peak_goal_enabled`, `peak_goal_kw` (always in kW), `peak_countdown`, `peak_vibrate_always`, `peak_open`, `history_open`, `appliances_open`, `appliances_enabled`, `appliance_help_seen`, `measuring`, `settings_closed` (the folded Settings sections, a string set). Files: `prices.json`, `recorder/GLyymmdd.CSV` (copies of the recorder's day files), `appliances.json`. Small settings and files only; no database.
- Backup (user, 2026-10-02): phone-to-phone transfer only, no cloud backup. `res/xml/data_extraction_rules.xml` excludes everything from cloud backup on Android 12+; `allowBackup="false"` covers Android 8 to 11, where it turns transfer off too.

## Data source

Per region; add new ones to `REGIONS`. Every utility found so far follows the **VSE/AES standard** for dynamic tariffs: the same query parameters and the same JSON as CKW below, so one parser serves all. `classify` is relative to each region's own prices, so it needs no per-utility tuning.

Checked 2026-09-29 (user's list in `research/swiss_energy_price_apis.csv`), each tested with the app's own request and code:

| Region id | Utility, tariff | URL (plus `tariff_type=integrated`) | Tomorrow out | Notes |
|---|---|---|---|---|
| `ckw` | CKW, `home_dynamic` | see below | ~11:20 → 12:00 | hourly prices |
| `ekz` | EKZ, `integrated_400D` (Energie Dynamisch + Netz 400D) | `https://api.tariffs.ekz.ch/v1/tariffs` | ~17:50 → 18:00 | 15-min prices; a `CHF_m` monthly fee comes before the `CHF_kWh` value, so the parser picks by unit. Without `tariff_name` EKZ returns a flat standard tariff. |
| `ekz_einsiedeln` | EKZ Einsiedeln, `integrated_400D_E` | same | ~17:50 → 18:00 | as EKZ |
| `groupe_e` | Groupe E, Vario | `https://api.tariffs.groupe-e.ch/v2/tariffs` (no `tariff_name`) | ~14:50 → 15:00 | 15-min prices, cheapest at noon and at night |
| `primeo` | Primeo Energie, `NetzDynamisch` | `https://tarife.primeo-energie.ch/api/v1/tariffs` | ~17:30 → 18:00 | hourly; only the grid part varies (energy flat 0.13), cheapest at night. Names from `/api/v1/tariffs/names`. From 2027 "Primeo Dynamisch" adds a dynamic energy part. |
| `primeo_avag` | AVAG (Aare Versorgungs AG, ~13 municipalities around Olten), `NetzDynamischAVAG` | same | ~17:30 → 18:00 | Primeo operates this grid |
| `primeo_elag` | ELAG (Elektra Gretzenbach AG), `NetzDynamischELAG` | same | ~17:30 → 18:00 | Primeo operates this grid |

Publication times are single observations (`publication_timestamp`), rounded up; if tomorrow isn't out yet at that time, the app just retries after the cooldown. None of the new APIs sent rate-limit headers; the 5-minute cooldown covers them. The Home Assistant integration `ehnid/swiss-dynamic-tariffs` supports the same set, which is a good place to look for new ones.

Not usable:
- **BKW:** `https://api.bkw.ch/api/dyntariffs/v1/tariffs` works, but has only `feed_in` (what BKW pays for solar), no consumption price.
- **Swisspower ESIT** (`esit.code-fabrik.ch`, AEW, IWB, EWL, SiL and others): per-utility prices need the customer's metering point number and a token issued to HEMS vendors (`/api/v1/metering_code`, 1 request per 5 min). The token-free `/api/v1/tariff_name` only knows generic names `D0` to `D3` and answered 504 after 60 s on every try on 2026-09-29.
- **Energy-Charts** (EPEX spot CH, hourly, EUR/MWh, no key) and **ENTSO-E** (needs a token): market prices, not a household tariff in Switzerland. Outside Switzerland, though, the spot price gives the same colour as a real dynamic tariff wherever the add-ons don't vary with time (Energy-Charts is CC BY for AT, BE, CH, CZ, DE-LU, DK1, DK2, FR, HU, IT-North, NL, NO2, PL, SE4, SI). Other countries, the whatwatt's meters by country and the peak tariffs (Flanders since 2023, Austria from 1 Jan 2027) are in [research/neighbouring_countries.md](research/neighbouring_countries.md); what the app does with them is in [Regions outside Switzerland](#regions-outside-switzerland).
- **ElCom** (LINDAS SPARQL, strompreis.elcom.admin.ch): static annual tariffs only. **strompreise-schweiz.ch:** needs an API key.


CKW (Central Switzerland): `GET https://e-ckw-public-data.de-c1.eu1.cloudhub.io/api/v1/netzinformationen/energie/dynamische-preise`

Query parameters (from CKW's "technische Voraussetzungen" page, tested 2026-09-29), all optional:
- `tariff_type`: `electricity`, `grid_usage`, `grid` or `integrated`. With one set, the response has only that component. The app asks for `integrated`.
- `tariff_name`: `home_dynamic` (under 50 MWh/year, households) or `business_dynamic`. The app asks for `home_dynamic`; without it the values were the same.
- `start_timestamp`, `end_timestamp`: send them in UTC (`2026-09-28T22:00:00Z`), and the response timestamps come back in UTC too (`2026-09-28T22:00Z`). Without them the API returns only today. The span may be at most 31 days (400 otherwise), past days work (August 2026 did), a range past the published data just ends there, and the slot starting at `end_timestamp` is included. The app requests today's local midnight to the midnight after tomorrow and drops that extra slot.

CKW serves only Central Switzerland (Zentralschweiz). HTTPS, no auth, `access-control-allow-origin: *`. Rate limited: `x-ratelimit-limit: 4` per window (the reset header said 999 s), hence the refresh policy above. When analysing prices by hand, save the responses rather than requesting again.

### Response schema (inspected 2026-09-28)

```json
{
  "publication_timestamp": "2026-09-27T11:19:17.128697+02:00",
  "prices": [
    {
      "start_timestamp": "2026-09-28T00:00+02:00",
      "end_timestamp":   "2026-09-28T00:15+02:00",
      "grid":        [{ "unit": "CHF_kWh", "value": 0.1074 }],
      "electricity": [{ "unit": "CHF_kWh", "value": 0.1200 }],
      "integrated":  [{ "unit": "CHF_kWh", "value": 0.2274 }],
      "grid_usage":  [{ "unit": "CHF_kWh", "value": 0.0771 }]
    }
  ]
}
```

- `prices`: quarter-hour slots, 96 per local day (00:00 to 24:00). Without query parameters only the current day.
- Tomorrow's prices are published from 12:00 (CKW's wording); `publication_timestamp` was 11:19 and 11:20 local on the days seen. The app looks for them from 12:00 (`CKW.tomorrowFrom`).
- The prices are **hourly**: all four quarters of an hour always had the same price (Aug and Sep 2026). CKW says it follows the forecast grid load, not the market.
- Timestamps: ISO 8601 with an explicit offset (Europe/Zurich, `+02:00` in summer and `+01:00` in winter, or `Z` when the request used UTC), minute precision, no seconds. Parse them with the offset (`OffsetDateTime`); don't assume a timezone.
- All components are single-element arrays with unit `CHF_kWh`: already CHF per kWh, so no conversion is needed.
- `integrated` = `grid` + `electricity` (the total price). On the inspected day `electricity` was flat at 0.12 and all the variation came from `grid` (and `grid_usage`, which is part of `grid`).
- CKW's stated range is 0.1 to 32 Rp/kWh for the dynamic part. Observed `integrated`, 1 Aug to 30 Sep 2026: the daily minimum was 0.1513 on nearly every day (a floor), the maximum 0.25 to 0.33.
- Every day has the same shape: one cheap valley from about 11:00 to 16:00 (PV). The night is **not** cheap (0.21 to 0.27). On weekdays the morning 06:00 to 09:00 is the peak; on weekends the dearest hour is usually midnight. The same hour varies only about ±1.5 Rp across weekdays. Exceptions happen: on 2026-09-09 the morning was 0.31 to 0.33 and the cheapest hour was 04:00.

### Classification (red / orange / green)

Signal: the `integrated` value of the slot where `start <= now < end` (`PriceSlot.covers`).

Reference window: the 24 hours starting at the current slot (`WINDOW`), about as long as appliances are usually delayed. If the data doesn't reach that far (tomorrow isn't out yet), the window moves back to end with the last known slot. The app fetches today and tomorrow, so before tomorrow is published (12:00 for CKW, later for others) the window is today and afterwards it's the next 24 hours.

Thresholds are relative to the window's range. With `min` and `max` taken over the window and `range = max - min`:
- **green** if `price <= min + range/3`
- **red** if `price >= min + 2*range/3`
- **orange** otherwise
- If `range == 0` (a flat day), show **orange**, since no time is better than any other.
- If no slot covers `now` (stale or missing data), show no colour. Display an error or "no data" state instead of guessing.

When now isn't green, `Status.nextGreen` is the first green slot later in the window, shown as the next good time. If tomorrow's prices are missing in the evening, there is none (today's valley is over), so nothing is shown.

Why: the goal is to shift load to times that are better for the grid than the rest of the same day, not to hit an absolute CHF price. A day-relative split survives tariff changes without retuning, which fixed CHF bands would not. It also only marks slots green or red when they are clearly apart from the rest. The user chose this over rank terciles, which force an even 1/3 split and on 2026-09-28 marked the moderate 20:00 to 23:00 evening red. `integrated` is used rather than `grid` so the colour stays correct if the energy component ever starts varying too.

Why the next 24 hours (checked 2026-09-29 on 1 Aug to 30 Sep 2026): you can't run an appliance in the past, so "wait if you can" should point to a cheaper time that is still coming. The old window, the calendar day, compared the evening with a noon that was over. That worked for CKW only because tomorrow's noon looks the same. Each quarter hour was scored by what waiting up to 24 h would really have saved:
- With the 24-hour window, green was 33% of the time, orange 22%, red 45%. Waiting would have saved on average 1.1 Rp/kWh at green, 6.9 at orange and 9.8 at red. Only 1.1% of greens missed a saving of more than 5 Rp, and no red had less than 2 Rp to gain.
- The calendar day scored almost the same (2.1% of greens missed more than 5 Rp) and differed in about 9% of hours, always orange against red. The main gain of the window is the next good time.
- Rejected: "the rest of today". Late in the evening it compares a few expensive hours with each other and shows green at 0.23 while tomorrow's noon is 0.15; 21% of its greens missed more than 5 Rp.
- Known weak point, left as is: the maximum is often one expensive hour (a spike to 0.33 moves the red line up and turns that evening orange). A percentile instead of `max` would fix it, but the effect is only orange against red.

## Peak load with whatwatt

Built step by step, as the user decides. Released in v0.7.0 (phases 1 to 3) and v0.8.0 (phase 4, the recorder).

### Household and tariff

- The household has **two meters, billed separately** (user, 2026-10-02): heat pump + boiler, and everything else. The peak tariff is billed per meter, so GridLoad only cares about the **household meter**; heat pump and boiler peaks are ignored. The whatwatt Go is on the household meter. An always-on Raspberry Pi is at home, but it isn't needed (see Recording while away).
- CKW's 2026 price sheet for grid products (Preisinformation Netzprodukte 2026, CKW Netz E/ES/Home dynamic) has a **Leistungstarif**: "Bei der Leistung wird die höchste während 15 Minuten beanspruchte mittlere Leistung (kW) im Monat gemessen und in Rechnung gestellt." It's per kW of the month's peak on top of the kWh prices, and **linear**: Home dynamic 1.00 CHF/kW per month excl. VAT (1.08 incl. 8.1% VAT); the standard single tariff E9 1.50 (1.62 incl. VAT); ES10 0.50. So lowering the monthly peak by 2 kW saves about 2 CHF a month.
- **No price brackets** (user, 2026-10-02): every kW above the month's highest quarter hour costs the same, so there's one line to watch, [the limit](#design-user-2026-10-02), not a ladder of brackets.
- Still to check: which product the household is on ("later"); whether the billed quarter hours are the fixed ones (:00, :15, :30, :45), like the price slots. Keep CHF amounts for the peak out of the code.

### Design (user, 2026-10-02)

- **Peak load needs a whatwatt.** No manual values, no typed-in appliances, no estimate: the meter measures everything (the [appliances](#appliances) are measured by it too). (v0.4/v0.5 built it on manually tracked appliances and CKW Excel imports; both were dropped, since the import mixes the household's two meters and only works for CKW.)
- **Both prices count** (Claude's suggestion, accepted): on CKW Home dynamic every kWh has its time-dependent price *and* the month's peak is billed per kW. Spot says *when* to run something, peak *how much at once*. So peak load is the spot screen plus the peak window, not a replacement.
- **The whatwatt switch** (`whatwatt_enabled`): off, the whatwatt isn't read and nothing about it appears on the main screen. The address stays saved while it's off. When it can't be read (away from home, rebooting), one quiet line, "whatwatt not reachable", instead of a stale value.
- **Code:** `WhatwattMeter` (app) reads the whatwatt every 5 s while visible and, with peak load on, copies the recorder's day files, checks the recorder, projects the current quarter and runs the Test and the recorder's actions; its state is `UiState.meter` (`MeterState`). The alarm stays in `MainViewModel` (it joins settings with meter data). While the address was edited in the last 10 s it isn't read (half-typed addresses).
- **Quarter hours from the energy register:** the billed peak is the average over fixed quarter hours, so take it from the meter's cumulative energy register at the quarter-hour boundaries, not from instantaneous power. The recorder on the whatwatt does it (see [The recorder](#the-recorder-phase-4)): it interpolates the register at each boundary between the readings either side, by the **meter's clock**, and saves a quarter only when both boundaries were seen with readings at most 30 s apart (at 3 kW at most ±0.1 kW of the quarter's average).
- **Projection** (`QuarterProjector`): this quarter hour = energy so far in it + the current draw for the time left, as an average kW. The register at the quarter's start is the end register of the recorder's last line, so it's exact. Without that line (after a whatwatt restart, or in the seconds before the line is copied), the draw before the first reading is assumed at the average since then (the current draw in the first minute), and after the quarter's first minute the window says "Estimated: the recorder has no start for this quarter hour." (user, 2026-10-03: estimate plus warning).
- **Storage:** the app keeps copies of the recorder's day files, `files/recorder/GLyymmdd.CSV`, under the same names (`RecorderFiles`), and parses this and last month's on start. About 3 KB a day.
- **The limit** (user, 2026-10-03; one line, labelled "limit" in the peak window and the history): the highest of the goal (when on), the **floor** and the month's highest quarter hour (`peakLine`). Anything up to the month's highest is billed anyway, and on a linear tariff a peak the biggest appliance sets by itself costs nothing extra; only stacking does. So the appliance that sets the month's peak isn't told to wait for it.
  - **The floor** (`peakFloor`): the heaviest quarter hour of the biggest appliance whose **Counts for the limit** is on (`heaviestQuarterKw`: the most its curve draws in any 15 minutes, so wherever in a quarter it starts), × 1.2 (`FLOOR_MARGIN`, for the house's base draw and some variation). Deterministic, from the measured curves only. Cooking (2.21 kW) gives 2.65. It counts only while the appliances panel is shown (`appliances_enabled`), so a hidden panel can't raise the limit unseen.
  - **The goal** is an override that can only raise the limit: a switch (`peak_goal_enabled`, default off) with a kW value (`peak_goal_kw`, a string), pre-filled with last month's highest (rounded to the power unit's step: 0.1 kW or 10 W) the first time it's switched on, if there is one. Off or blank, it doesn't count.
  - With no limit (nothing recorded, no appliance, no goal), the window shows only the bars, with no "kW free" and no alarm.
- **Alarm, in the app only:** when this quarter hour's projection reaches the limit (`isPeakWarning`; no margin since 2026-10-03, the user's choice: the floor's 20% is the margin, and "kW free" and the red bar agree), the current bar turns red with a warning line, and the phone vibrates once per quarter hour (400 ms), only with peak load on while the app is open. **Vibrate at the limit** (user, 2026-10-03; `peak_vibrate_always`): "Unless silent" (default) vibrates as a notification, "Always" as an alarm, in silent mode too. A vibration without a usage counts as touch feedback, which silent mode turns off (seen on the Fairphone 6: `dumpsys vibrator_manager` showed every alarm `ignored_for_settings`). No background service and no notification permission for now.
- **The peak window** (`PeakWindow.kt`, user, 2026-10-03): the spot colour stays the background; below the price a white panel. Its **header** is "1.3 kW free" (or "kW over"; from the values as drawn, rounded to the unit's step, so a "0.9" limit and a "0.8" bar always give "0.1 kW free"; the red bar and vibration use the exact values, so a bar right at the limit can show "0.0 kW free" in red), with the countdown to the next quarter hour on the right ("7 min left", `peak_countdown`, default off; waiting a few minutes before the kettle or oven often avoids a peak) and ▴/▾. Open, it holds a vertical scale with bars for the **three previous recorded quarter hours** (with "now", the last hour; user, 2026-10-03) (`PAST_BARS`, grey, labelled with their start time; a missed quarter shows "–"; at the start of a month they come from last month) this quarter hour's projection ("now", 1.6× as wide as the past bars, in the middle) and three columns for the coming quarter hours (`FUTURE_BARS`, empty with their times unless a [preview](#ok-or-wait) fills them, so "now" stays put; user, 2026-10-03), and the limit (one solid line, "2.6 limit"; user, 2026-10-03: no separate lines for the highest and the goal). Each bar's value is **above** it (never inside, so small bars look the same as big ones), moved off a line crossing it. Below the scale the warning ("This quarter hour sets a new peak.") and the recorder's state when something is wrong (red, ends in "›", tap for Settings; muted for "Recorder started. First quarter hour at 00:15."). **Collapsed**, only the header shows, but the warning and the recorder's red line stay, and the header turns red with the bar, so the alarm is never hidden. "Recorded since" and the gaps are in Settings → Recorder (opened).
- **Without a reading:** the panel stays, with the limit and the past bars (from the copied files), no current bar, and "whatwatt not reachable" as its header. With no limit (nothing recorded, no appliance, no goal) the header shows the draw now.

### Power unit

`power_unit` (user, 2026-10-03), under Measurement: **kW** (default, one decimal) or **W** (whole watts, rounded to 10 W, e.g. "1340 W free", since appliances are labelled in W). W and kW are the only units for electrical power in common use in the EU and CH (MW is too big, PS/hp isn't used for electricity, kVA is apparent power, which the meter doesn't give). It applies to everything the whatwatt shows: the cost line, the peak window's header, scale and labels, the goal field and the history. The goal is saved in kW either way. The decimal separator follows the phone's locale already. Rp/kWh against ct/kWh belongs to the country, when a second one comes.

### History

A panel below the peak window (user, 2026-10-03: "start and we will see if it's good"), also from the recorder's copied files, so it's complete on open. First version: one bar per day of this month, that day's highest quarter hour, with the limit across it, as in the peak window. The day of the month's highest is red, today dark, the other days grey (user, 2026-10-03). The bars are thin; no tap-for-value (too thin to hit). Collapsed header: the month's highest and when it happened ("Highest 4.2 kW · 2 Oct 18:30"); before anything is recorded, "No quarter hours recorded yet". Days before the recorder started, and today's remaining hours, have no bar.
- **Full screen** (`HistoryScreen`, user, 2026-10-03): tapping the open chart opens a white screen like Settings (← "History"). ‹ › switches between this month and last month (both already loaded, nothing downloaded), with the month's highest and its day bars, taller. Tapping a day shades it (from the axis top to the baseline) and shows its quarter hours below (at first the day of the month's highest): "Sat 3 Oct · highest 2.4 kW at 18:30" and one bar per recorded quarter hour in its slot (`DayQuarters` in core: a missed one leaves a gap; 92 or 100 slots on the DST days), the month's highest red, the day's own highest dark, hour labels every 6 hours. Both charts share one scale. The limit is drawn for this month only, since its goal and floor are today's. No tap-for-value on the quarter bars; taps outside the day bars' plot (axis, limit label) do nothing. After Android kills the app with the screen open, it shows "No quarter hours recorded." for the moment until the files load (accepted); the same line shows for a month with nothing recorded (user, 2026-10-03: the month is in the row above). The help says it can be tapped; the screen has no hint.

### Recording while away

The phone reaches the whatwatt only on home Wi-Fi (or a VPN, see phase 5), and the app reads it only while open (no background work). **Requirement (user, 2026-10-02):** the typical use is "open the app, look for 10 s, know what to do", so the month's highest must be complete within a second of opening, not after a download. Chosen: **the GridLoad recorder on the whatwatt** (phase 4), a Berry script that records every quarter hour 24/7 into small day files on the SD card (~2.7 KB/day), which the app fetches on open in well under a second. It also makes the projection exact from the first second and gives every phone the same quarters. Rejected (2026-10-02/03), so don't reopen them:
- The meter's maximum demand register: the Kamstrup over KMP doesn't report one.
- Downloading the SD-card CSV log on open: whole-day files only (no `Range`) at ~12.7 KB/s, and a full-speed download drains the supercap (3.76 → 3.2 V for 265 KB; the second in a row rebooted it, twice). ≤ 8 KB/s holds, but a day at 30 s (~720 KB) then takes ~2 min.
- The app recording while open, as in v0.7, as a fallback (user, 2026-10-03): its highest is mostly a guess and it doubled the code paths. Instead, **no fallback and a rigorous warning culture**: the app says precisely what's wrong, so the user can fix it (or ask someone).
- Kept in reserve: a WorkManager job downloading the CSV (Android delays it by hours; each phone downloads the whole day). Rejected: a foreground service polling all day (permanent notification, battery, Android 15's 6 h/day cap on `dataSync`) and a logger on the Pi (extra hardware).

### The recorder (phase 4)

Built 2026-10-03; the script, its tests on the device and the measurements are in [research/whatwatt_berry_script.md](research/whatwatt_berry_script.md).
- **Requirements** (user, 2026-10-03, to be stated clearly; in the README, the whatwatt and peak load ⓘ and the help): a whatwatt Go (CHF 90), the adapter for the meter (Kamstrup OMNIPOWER: CHF 20), the Plus licence (CHF 19), the meter's key from the utility, a microSD card in the whatwatt (any size: ~1 MB a year), the one Berry script slot free, the whatwatt on 2.4 GHz Wi-Fi with a fixed address and Device Protection off, and the phone on the home network (or a VPN) for live values. Prices only in the README, not in the app.
- **The script** is `core/src/main/resources/gridload_recorder.be` (`RECORDER_SCRIPT`, packaged in the APK as a Java resource), GPL source like the rest. Its first line is `# GridLoad recorder <n>` (`RECORDER_VERSION`, now 2): the app's own script is recognised by it and an older one is updated by itself (once per app start); a script without the marker is someone else's and is **never** replaced or removed (`installRecorder`/`removeRecorder` check it themselves). No `print`. ~1.7 KB of the 8191 allowed.
- **Day files:** `/sdcard/GLyymmdd.CSV` (8.3 names), named by the local date (`time.dump`, the device's timezone) of each line's time, so the quarter starting 23:45 goes into that day's file. The app reads each quarter by its UTC time and takes months and days in the region's `zone`; the names only choose which files to copy (`RecorderFiles.sync`, up to today in the region's zone), so a whatwatt set to a zone ahead of the region's would have each day's last quarters copied only after midnight. Keep the whatwatt's time zone the region's. Lines: `<start, UTC epoch s>,<kWh>,<register at its end>` per quarter, and `<time>,start` at each start of the script (its first reading), which explains gaps and tells when the first quarter is due. The DST night needs nothing special. Without an SD card the write just fails. A missing file answers **500** (not 404).
- **Install** (Settings → Recorder → Install, only when the slot is empty): `PUT /api/v1/berry?run=false`, `POST /api/v1/berry` (text/plain; POST neither stops nor starts a script), `PUT /api/v1/settings` `{"services":{"berry":{"auto_run":true,"run_delay":60}}}` (60 s is the shortest delay), `PUT ?run=true`. **Start/Fix**: the settings, plus `run=true` if stopped. **Remove** (after a confirmation dialog saying that peak load stops on every phone using this whatwatt and that quarter hours while it's removed are lost, the recorded ones stay): `run=false`, `DELETE`, `auto_run: false`; the day files stay on the card. After Install or Start the app waits 6 s for the start line, then checks again.
- **Sync** (`WhatwattMeter.sync`, only with peak load on): `fetchRecorderStatus` (`/api/v1/system` for `services.berry.execution_status.state` (`"RUNNING"`), `sd_card.installed`, `device.time_since_boot`; `/api/v1/settings` for `auto_run`/`run_delay`; `GET /api/v1/berry` for the script), then `RecorderFiles.sync`: on a phone with no day file of this and last month yet it lists `/sdcard/` once and copies all of them; afterwards only its newest day and the days after it (past days don't change), so a normal sync is 3 small status requests plus one or two ~3 KB files. When: with the first reading, when the next line is due (5 s after the boundary, then every 15 s, after 2 min every minute), every 15 min, and every minute until a check succeeds. The copied files show at once on start, before anything is fetched.
- **Warnings** (user, 2026-10-03; `checkRecorder` → `RecorderCheck`, texts in `recorderLine`), the first that applies: no SD card · not installed (Install) · another script ("GridLoad doesn't replace it") · older recorder (updated by itself) · whatwatt restarted, starts at hh:mm (auto-run pending) · stopped (Start; any `state` other than `IDLE` in brackets) · won't start after a restart (`auto_run` off; Fix) · silent: nothing saved since hh:mm (no line a minute after one was due; or "started at hh:mm, but hasn't saved a quarter hour") · waiting: "Recorder started. First quarter hour at hh:mm." (not a warning) · OK ("Installed and recording." in Settings). Gaps separately, in Settings → Recorder (opened) only (user, 2026-10-03: "if we have gaps we have gaps", the help says once what they mean): this month's quarters missing from its first recorded quarter (or the month's start, if it recorded last month) up to the last check (`missingQuarters`), with a restart right after the last gap named. While the whatwatt isn't reachable, only "whatwatt not reachable" shows, and the gaps stay as of the last check.
- **Frozen at v2 (user, 2026-10-03):** the script stays exactly as it is: no v3, no minute log, no other change to `gridload_recorder.be`, and nothing new sent to the whatwatt. It was tested many times, it's at the limit of what Berry and the meter's power supply handle stably, and the billed peak depends on it. Don't propose script changes; new features build on its quarter hours as they are (e.g. the appliances panel, [research/appliances.md](research/appliances.md)).
- **Two phones:** the recorder is device state, so every phone sees the same script, files and warnings; either can install or remove it.

Docs: https://documentation.whatwatt.ch.

AF1 (`protocol` `"KMP"`, `interface` `"TTL"`), through the Kamstrup adapter. 2.4 GHz Wi-Fi, RSSI −64 to −72 at the meter. Powered by the meter alone (no socket there). Kamstrup meters supply little power, so polling stays gentle. It stayed up through 2 s polls for a minute and an hour of 15 s SD logging (check `device.last_reboot` in `/api/v1/system`). At home: `http://192.168.0.36` (DHCP reservation set, 2026-10-02), hostname `whatwatt-7C02F0`. `avahi-browse` didn't find it, so no DNS-SD discovery.
- **Bought:** whatwatt Go (CHF 90) + the Kamstrup Omnipower adapter (CHF 20) + the Plus licence (CHF 19, one-time), activated 2026-10-02. The licence sits **on the device** (`device.license.type` `"PLUS"` in `/api/v1/system`), so every phone on the home network can use it. No whatwatt account was made; GridLoad must not need one.

- **`meter.status`:** `"NOT CONNECTED"` with no meter (interface `"NONE"`), `"KEY REQUIRED"` before the key, `"OK"` after it (`enc_en: true`). Trust the values only when it's `"OK"`.
- **Auth:** Device Protection is off, and the API answers without credentials. With it on, every endpoint answers 401 with `WWW-Authenticate: Digest realm="whatwatt-<id>", algorithm=MD5-sess, qop=auth`, empty username. `HttpURLConnection` doesn't do Digest, so the app doesn't either: on 401, Test says to turn Device Protection off (user, 2026-10-02). A lockout is fixed by a factory reset (hold the button 10 s or more, then redo the Wi-Fi setup over AP mode).
- **`GET /api/v1/report`** (needs Plus, else `404` with body `License required`). The app reads it (user, 2026-10-02): unlike the stream, several readers can poll at once, e.g. two phones in the household. Tested 2026-10-02 with two phones, one on home Wi-Fi and one over Tailscale, each polling every 5 s for 20 min: both always showed the same reading, the recorded 21:30 quarter matched the SD log (0.2282 against 0.2283 kWh), and the whatwatt didn't reboot. With the recorder (phase 4), both phones copy the same quarter hours. Real fields (all modelled nullable):
  - `report.instantaneous_power.active.positive.total`: kW, the current draw.
  - `report.energy.active.positive.total`: kWh imported, the register for the quarter hours; also `t1`/`t2` (tariff registers, which add up to the total). Resolution **0.001 kWh**, so a 0.2 kW quarter hour (50 Wh) is about ±2% off.
  - `report.id`: +1 with each meter reading, every ~4.2 s (`report.interval`), so an unchanged `id` means stale data. It restarts at boot.
  - Timestamps: `report.date_time_utc` / `system.date_time_utc` are real UTC. **`date_time` ends in `Z` but is local time** (firmware quirk), so never use it. `date_time_local` has the offset. `report.*` is the **meter's** clock (equal to `meter.date`/`meter.time` in `/api/v1/system`), `system.*` the whatwatt's: against the PC (NTP), the meter's was right to within its 4.2 s reading interval, the whatwatt's 22 s fast, though it says NTP synced (2026-10-02). The app uses the meter's.
  - `meter.status`, `meter.id` (the meter number), `system.boot_id`, `system.time_since_boot`.
- **`GET /api/v1/report/objects`** (Plus): empty for this meter. KMP isn't DLMS, so there are no OBIS objects and **no maximum demand register**.
- **`GET /api/v1/live`:** an SSE stream, `event: live` with flat JSON (`P_In` kW, `E_In` kWh, `E_In_T1/T2`, `Date`, `Time` local), one event per meter reading. It works **without** the Plus licence, but only one client at a time: a new one closes the previous stream. Not used, because of that limit; it's the fallback if a licence-free option is ever wanted.
- **SD card** (SDHC, installed): logging turned on 2026-10-02 via `PUT /api/v1/settings` `{"services":{"sd":{"enable":true}}}` (PUT merges partial settings). `services.sd.frequency` is in **seconds** (15 = a row every ~15–17 s, every 4th reading). `GET /sdcard/` lists the files (503 without a card; the listed `size` lagged at 0 while the file had rows), `GET /sdcard/YYYYMMDD.CSV` downloads one day: a header line, then ~250 bytes per row (~1.2 MB/day at 15 s). Columns include `RID` (= `report.id`), `TIME` (**local, despite the `Z`**, as above; on the meter's clock), `MSTAT`, `EAP_T`/`EAP_T1`/`EAP_T2` (the register, kWh), `IPAP_T` (kW), `RP` (report period, ms). `MDAP_*` (maximum demand) exist but are empty for this meter. Skip rows that aren't `MSTAT` `OK` or where the register goes backwards. `RID` can restart without a reboot (3834 → 1 at 21:48 on 2026-10-02), so order rows by `TIME`. Set to 30 s on 2026-10-02 as the reference for validating the recorder, and **turned off** on 2026-10-03 after the validation (`services.sd.enable: false`). Downloads: see Recording while away.
- **Firmware and SD card for the recorder:** Berry since firmware 2.0.0, per whatwatt's docs and the user's device, which reported `services.berry` in `/api/v1/system` on 2.0.0 (`private/whatwatt_system_2026-10-02.json`); the recorder is tested only on 2.8.2. No firmware check, since no version is known to fail; the manual says to update firmware on USB power, since Kamstrup meters may not supply enough. The manual requires a FAT32 microSD card, and the antenna on before power (the device calibrates its radio at startup); on meter power alone it doesn't start until Wi-Fi is set up.
- **Berry on the whatwatt** (tested on the device 2026-10-02; details, the script and the test log in [research/whatwatt_berry_script.md](research/whatwatt_berry_script.md)): one script slot, `GET`/`POST`/`DELETE /api/v1/berry` (404 = empty; max 8191 bytes; POST saves without stopping or starting), `PUT /api/v1/berry?run=true|false`, console at `/api/v1/berry/console` (SSE, live only, one client); `PUT /api/v1/berry` without a query answers `{"run": true|false}`. `/api/v1/system` has `services.berry.execution_status.state` (`"RUNNING"`, `"IDLE"` when stopped or with no script (seen 2026-10-03); other values not documented) and `sd_card` (`installed`, `type`, `size`, no free space). Auto-start: `services.berry.auto_run` with `run_delay` **60 to 86400 s** (default 300). `ww.onreport` fires on every meter reading; its `timestamp` is the **meter's clock** (equal to `report.date_time_utc`). `open()` works on `/sdcard/...` (write, append, read), and the file is then served by `GET /sdcard/<name>`. `json`, `time`, `string`, `math` and `gc` exist; `path` doesn't. Reals are double, ints 64-bit, so the register is exact (`str()` just prints 6 digits; use `string.format`). `time.dump(epoch)` gives **local** time (the device's timezone). The draft script's first quarter (23:15–23:30) matched the CSV log within 0.0005 kWh.

Declared in the manifest, and asked for on the first Test (`SDK_INT >= 37`). Without it, connections just time out, hence the check before testing. The picker exemption (`NsdManager` + `FLAG_SHOW_PICKER`) isn't used, since the whatwatt didn't show up over DNS-SD. The user's phone was on API 36 on 2026-10-02, so the permission prompt is untested.

## Appliances

Measured appliances with OK or WAIT per row (user, 2026-10-03). The reasoning, the rejected options and the test measurements are in [research/appliances.md](research/appliances.md). It reverses v0.6's "no appliance list", which was against *typed-in* appliances whose values were guesses: here every appliance is **measured** by the whatwatt, and there are no typed watts (user, 2026-10-03). Code: `core/.../Appliances.kt` (the model, its JSON, `doneAt`, `measure`, `withRunTime`, `heaviestQuarterKw`, `peakFloor`, `quarterLoads`, `fitsPeak`, `runPrice`, `advise`), `AppliancesPanel.kt`, and the appliance state and actions in `MainViewModel`.

- **The panel:** the second panel, between the peak window and the history, collapsible like them (`appliances_open`). Header "Appliances" (bold, 20 sp; no emoji, user 2026-10-03), collapsed with a summary ("2 OK · 1 wait", or "Measuring"). Rows: the name, a green **OK** or orange **WAIT** chip (black text; user, 2026-10-03: not red), and the "when" line below. Tap a row to preview its run in the peak window (tinted while shown; tap again or × to close), hold it for its edit sheet (user, 2026-10-03). **+** at the end, with a hint while the list is empty. Needs peak load on (the whatwatt and the recorder), like the other panels, and can be hidden in Settings (`appliances_enabled`).
- **The appliance:** the name (the key, unique), the **curve** (its extra draw above the household's base, as pieces back to back from the start: `min` minutes at `kw`), **Can wait** (default on: the price counts too, e.g. a dishwasher; off: only the peak, e.g. a kettle), **Counts for the limit** (default on: its heaviest quarter hour can raise the [floor](#design-user-2026-10-02); off for one that shouldn't, e.g. one rarely used) and **Start delay** (none · 30 min · 1 h; with it set, the advice is the delay to set on the appliance). The run time, the kWh and the power (the highest piece) are derived. No programme field (another programme is another appliance, "Dishwasher 65°"), no category field, no emoji (later).
- **Storage:** `files/appliances.json`, a list of `{name, curve, canWait, delayMinutes, countsForLimit}` (`countsForLimit` defaults to true, so files and exports from v0.10 load). Prefs: `appliances_open`, `appliances_enabled` (the panel shown at all), `appliance_help_seen` (the setup help was shown once), `measuring` (a measurement under way, below).
- **Export and import:** Settings → Mode → Appliances, **Export** and **Import** through Android's file picker (`CreateDocument`/`OpenDocument`, no permission, no cloud). Same JSON as `appliances.json`. Import adds the file's appliances; one with the same name replaces the existing one in place. An unreadable file changes nothing and says so; so does one with a name twice or a curve whose last piece is at 0 kW (`parseAppliances`).

### Measuring

From the recorder's quarter hours as they are, plus the jump in the live draw at the start (user, 2026-10-03). The app is needed only at the start and after the run, and 15-minute resolution matches the billed peak. The recorder stays at v2: a minute log was rejected.
- **The flow:** **+** opens the setup help (by itself the first time), then the sheet (Name, Can wait, Start delay) and **Start**, before switching the appliance on. Start is blocked, with the reason, while another measurement runs, without a reading, or with a recorder warning. The row then shows the jump live and survives leaving the app. **Done** when the appliance has finished (it beeps); not detected, since eco programmes sit at the base for long stretches. Until the quarters before Done's are saved, the row says when the result comes; then the run time, kWh, power and the curve, with **Save** or **Discard** (Discard asks first, like Delete; user, 2026-10-03). Measure again (in the edit sheet) replaces the curve.
- **`measuring`** (JSON in the prefs): the appliance as entered, Start's and Done's times, the live draw just before the start (`beforeKw`, only for the jump), the base (`baseKw`) and the energy in Done's quarter up to Done (`doneKwh`).
- **Done** (`doneAt`, user, 2026-10-03): the energy used so far in Done's quarter hour (`Projection.usedKwh`, exact from the register, like the base at Start), so the household's draw after Done doesn't count and the result needs only the recorded quarters before Done's. Only from a fresh (under 15 s) exact reading: a reading from just before the boundary puts Done at the boundary; a stale or estimated one, and a measurement saved before `doneKwh`, fall back to the recorder's whole quarter. A Done on a boundary ends the quarter before.
- **The base** subtracted from the quarters: the average in the start's own quarter hour before Start (`Projection.baseKw`, exact from the register) when Start is at least 5 minutes into the quarter; else the recorder's quarter before; else the live reading. (A busy quarter before, like lunch at 0.58 kW, would eat a kettle's 0.1 kWh.)
- **The curve:** each quarter from the start's to Done's minus `base × 0.25 h` (Done's: `doneKwh` minus the base up to Done; at least 0), spread evenly over the part of the quarter between Start and Done, so a run started at :07 lines up when projected onto other starts. Not the jump at the end: with several appliances it's all of them at once (cooking's last quarter became 15 s at 5 kW). Quiet quarters at the end (under 0.01 kWh) and zero-length pieces are dropped. A quarter missing in between, or nothing above the base, says so and asks to measure again.
- **The setup help** (`MeasureHelp`, as drafted with the user; ⓘ in the sheet's title reopens it): "Measuring an appliance": the recorder recording, at home with GridLoad open at the switch-on until the jump shows, nothing else switched on or off until Done, a quiet time, the usual programme to its end, Done as soon as it has finished, the result usually right after Done, only appliances on the whatwatt's meter.

### Variants

(user, 2026-10-03: "variants instead of categories", scalable, not hardcoded, robust.) Fixed appliances, composite actions (cooking) and dynamic ones (a kettle, an oven for longer) differ only in how the curve is made. Fixed ones and actions are measured once as a whole. **Add a variant** in every appliance's edit sheet takes another **run time** (min): the curve's start stays as measured and its last phase is stretched or cut (`List<Piece>.withRunTime`: the last piece runs longer, or the pieces past the run time are dropped). An oven keeps its preheat and cycles longer; a kettle is one piece at fixed power, so this is linear. The optional **From water ›** helper (Measured with, L to 100 °C, default 1; Water, L; Temperature 100 · 90 · 80 · 70 °C) fills in the run time with `waterShare` = litres / measured litres × (T − 15 °C) / 85: tap water at 15 °C, the kettle's own heat-up ignored. The name is suggested from the original's with its trailing amount replaced ("Kettle 1 L" → "Kettle 1.5 L", "Cooking 34 min" → "Cooking 60 min", and a variant's "· 80 °C" goes too) until one is typed. A variant keeps Can wait, Counts for the limit and Start delay and is saved as a plain curve, not a link: renaming or deleting the original can't break it, and re-measuring the original means adding its variants again. So a variant of a cut variant stretches what's left, not the original's last phase (user, 2026-10-03: left as is). Left out until needed: power levels (measure the action as cooked) and combining appliances.

### OK or WAIT

Recomputed with each reading and each minute, for each appliance, for starting it now (`advise`). A what-if per row, not tracking: the app doesn't know what runs, but a running appliance raises the draw and the other rows react.
- **Peak:** for each quarter the run touches, the household (this quarter: the peak window's projection; later ones: the draw now) plus the curve's energy in that quarter as an average kW (energy × 4). It fits if no quarter reaches the limit (`peakLine`, `isPeakWarning`), where the peak window's bar turns red, so the two always agree. No limit: the peak never blocks.
- **Price** (only with Can wait): the run's price for a start is its energy-weighted average, Σ kWh(slot) × price / Σ kWh, so a dishwasher's heavy first half counts most. **Candidates** (user, 2026-10-03): now, then each :00, :15, :30, :45 (no minute-level starts), or with a start delay now + 1, 2, … steps, starting within the 24-hour window. Only runs ending within the known prices compete. OK if now is in the cheapest third of their range (the main colour's thirds); all equal: OK. If even now runs past the known prices, the price isn't judged and the row says "Tomorrow's prices aren't out yet." (user, 2026-10-03).
- **The row:** **OK** when the peak fits and, with Can wait, the price is OK. **WAIT** otherwise, with the first candidate where both pass: "Sets a new peak · at 14:15", "Sets a new peak right now" (no start in the window fits; not "at any start", since later quarters only assume the draw now and the app can't see when a running appliance ends), "Cheaper at 11:00"; with a start delay "Sets a new peak · Delay 1 h" and "Cheaper · Delay 3 h" (to the nearest minute); past midnight without "at": "Cheaper tomorrow 10:00" (user, 2026-10-03). When every cheaper start sets a peak, now is OK. Without a reading: "–"; also for a Can-wait appliance while there are no prices at all (none fetched, or the fetch failed), unless starting now sets a new peak (user, 2026-10-03). A measurement under way shows its measuring row instead.
- A row looks at the whole run, so it can differ from the main colour (in the help).
- **Preview** (user, 2026-10-03): tapping a row shows its run started now in the peak window, which opens and scrolls into view. The "now" and coming columns stack the house (dark; later quarters at the draw now) and the appliance (blue; red in a quarter that reaches the limit), from `quarterLoads`, the same numbers `fitsPeak` judges, so the bars and the chip always agree. Header "0.2 kW free with Cooking" (the run's tightest quarter, red if any warns) with × in place of ▴; below the scale a legend, "Then n more quarter hours, up to x kW." for a run past the columns, and the row's line (or "OK to start now."). Kept as `UiState.preview` (not saved); gone without a reading or when the appliance is renamed, deleted or measured again.
- Where in the quarter you start matters: a run whose heavy part fills a whole quarter can fit when started mid-quarter (split across two) and not at a boundary, so a row can turn from WAIT to OK within a quarter.

## Regions outside Switzerland

Decided with the user on 2026-10-03, plan approved, not started (the user says when); the steps are in the skill, the facts and sources in [research/neighbouring_countries.md](research/neighbouring_countries.md).

- **Wave 1** (user, 2026-10-03), released before 1 Jan 2027, when Austria starts billing the peak: **Austria** and **Flanders** with peak load; **Wallonia and Brussels**, **Germany**, **Luxembourg**, the **Netherlands** and **Liechtenstein** with prices only. All from Energy-Charts' day-ahead prices (CC BY 4.0, "Bundesnetzagentur | SMARD.de"), one parser. Wallonia and Brussels are offered with a note that their time-of-use grid fee isn't in the colour. Liechtenstein shows € like the source, though households pay CHF (user, 2026-10-03: fine for now; CHF is a rainy-day task in the skill). In English.
- **Next phases, in order** (user, 2026-10-03): German; Spain (REE PVPC); Denmark (spot plus the grid operator's tariff); Norway only once Norgespris' 2027 terms are known. Czechia, Poland, Hungary and Slovenia aren't planned.
- **Meter reader** (user, 2026-10-03): the whatwatt stays the only one, and peak load is offered abroad for anyone who has one (no EU shop is known). A reader sold in the EU (HomeWizard P1 or similar) is a future task; it has no recorder, so keeping the month's highest complete is its first question.
- **The own price in spot regions** (user, 2026-10-03): the market price isn't what households pay, so Settings → Region takes an **add-on** (ct/kWh excl. VAT: supplier markup, grid fee per kWh, levies) and **VAT** (%, preset per country), and the price shown is (spot + add-on) × (1 + VAT), which never changes the colour. Not a multiplier: the fixed part is larger than the spot price, and spot can be negative. Until the add-on is entered: "Market price 11.3 ct/kWh", no cost line, and "Set your price ›" to the fields.
- **The minimum** (user, 2026-10-03): the least peak a tariff bills, per region (`Region.minimumKw`: Austria 2 kW, Flanders 2.5 kW, CKW 0, null where no peak is billed). The limit is the highest of the goal, the [floor](#design-user-2026-10-02) (the biggest appliance × 1.2, unchanged), the minimum and the month's highest. Austria's "or 20% of the contracted capacity" is left to the goal. Flanders bills the average of the last 12 monthly peaks, which changes the money, not the line.
- **Peak load where no peak is billed** (user, 2026-10-03: "we should not lock features"): it works as in Switzerland, stays off by default, and once switched on, the app says the region doesn't bill a peak. Of the Swiss regions only CKW bills a household peak (checked 2026-10-03; Groupe E unconfirmed, treated as none), so the other six get this too. Never a restriction: users there keep what they set and can switch it on.
- **Fixed-price households** (user, 2026-10-03), mostly in Germany: everything stays the same; the help says the colour saves money only on a dynamic tariff and still shows when the grid has power to spare.

## Conventions

- **Simplest approach that works.** Don't over-engineer and don't clutter the UI or the code: no extra screens, options, layers or abstractions until they are needed. When unsure, or when a simpler idea or a good idea comes up, ask the user instead of deciding alone.
- **No dead code** (user, 2026-10-02): remove what isn't used; git history keeps it.
- **Migrations** go two releases after F-Droid has shipped past the version that needed them (see [Decided](#decided)).
- A periodic declutter pass (user, 2026-10-02) follows [.claude/skills/build-gridload-android/declutter.md](.claude/skills/build-gridload-android/declutter.md).
- Commit only when asked; the user pushes.
